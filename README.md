# Final_Project.sql — University Course Management System (UniversityCMS)

## 1. Project Overview

This document explains, query by query, every SQL statement in **`Final_Project.sql`**.
For each query it states the **objective** (what the query is meant to accomplish),
shows the **exact SQL** from the script, and shows the **real output table** produced
when the script is run against the sample data.

All outputs below were generated by actually executing the script (adapted to run on
SQLite, since MySQL is not available in this environment) with a small Python
verification harness — see [Section 4](#4-how-the-outputs-were-generated) for details.
The table structure, data, and query logic are **identical** to `Final_Project.sql`;
only three MySQL-only functions (`YEAR()`, `DATEDIFF()`, `CONCAT()`) were mapped to
their SQLite equivalents so the queries could actually be run and their true output
captured, rather than typed by hand.

## 2. Database Objective

`UniversityCMS` is a small relational database that models a university's course
catalog and enrollment records. Its purpose is to demonstrate core relational
database design and SQL skills, including:

- Designing a normalized schema with primary keys and foreign keys across five
  related entities (Departments, Students, Instructors, Courses, Enrollments).
- Performing full CRUD operations (Create, Read, Update, Delete).
- Writing filtering, aggregation, and grouping queries (`WHERE`, `GROUP BY`, `HAVING`).
- Combining data across tables with `INNER JOIN`, `LEFT JOIN`, and subqueries.
- Using string, date, and window functions (`CONCAT`, `YEAR`, `DATEDIFF`,
  `COUNT() OVER`) and conditional logic (`CASE WHEN`).

## 3. Schema

| Table | Purpose | Key Columns |
| --- | --- | --- |
| `Departments` | Academic departments | `DepartmentID` (PK) |
| `Students` | Enrolled students | `StudentID` (PK), unique `Email` |
| `Instructors` | Teaching staff | `InstructorID` (PK), `DepartmentID` (FK), `Salary` |
| `Courses` | Courses offered | `CourseID` (PK), `DepartmentID` (FK), `Credits` |
| `Enrollments` | Student ↔ Course link table | `EnrollmentID` (PK), `StudentID` (FK), `CourseID` (FK) |

**Sample data loaded:** 2 departments, 2 students, 2 instructors, 2 courses,
2 enrollments (one student per course). Because the sample dataset is intentionally
small, queries that filter for large groups (e.g. "more than 5 students in a course")
correctly return **no rows** — this shows the filter logic working as intended, not
an error.

## Query 4 — Courses With More Than 5 Enrolled Students

**Objective:** Count students per course and keep only courses where that count exceeds 5, using `GROUP BY` with a `HAVING` filter on the aggregate.

**Query**
```sql
SELECT c.CourseID, c.CourseName, COUNT(e.StudentID) AS StudentCount
FROM Courses c
JOIN Enrollments e ON c.CourseID = e.CourseID
GROUP BY c.CourseID, c.CourseName
HAVING COUNT(e.StudentID) > 5;
```

| *(no rows)* | *(no rows)* | *(no rows)* |

> Each course only has 1 enrolled student in the sample data, so none exceed the `> 5` threshold — the empty result is expected.


## Query 5 — Students Enrolled in BOTH Courses (AND logic)

**Objective:** Find students enrolled in **both** 'Introduction to SQL' *and* 'Data Structures' by grouping per student and requiring `COUNT(DISTINCT CourseName) = 2`.

**Query**
```sql
SELECT s.StudentID, s.FirstName, s.LastName
FROM Students s
JOIN Enrollments e ON s.StudentID = e.StudentID
JOIN Courses c ON e.CourseID = c.CourseID
WHERE c.CourseName IN ('Introduction to SQL', 'Data Structures')
GROUP BY s.StudentID, s.FirstName, s.LastName
HAVING COUNT(DISTINCT c.CourseName) = 2;
```

| *(no rows)* | *(no rows)* | *(no rows)* |

## Query 11 — LEFT JOIN: All Students, With Courses if Any

**Objective:** Return **every** student regardless of whether they are enrolled in a course, using `LEFT JOIN` so unmatched students would still appear (with `NULL` course fields) if they existed.

## Query 12 — Subquery: Students in Popular Courses (>10 students)

**Objective:** Use a nested subquery to first identify courses with more than 10 enrolled students, then find which students are enrolled in those courses.

**Query**
```sql
SELECT DISTINCT s.StudentID, s.FirstName, s.LastName
FROM Students s
WHERE s.StudentID IN (
    SELECT e.StudentID
    FROM Enrollments e
    WHERE e.CourseID IN (
        SELECT CourseID
        FROM Enrollments
        GROUP BY CourseID
        HAVING COUNT(StudentID) > 10
    )
);
```

**Output**

| StudentID | FirstName | LastName |
| --- | --- | --- |
| *(no rows)* | *(no rows)* | *(no rows)* |

> No course has more than 10 enrolled students in the sample data, so the inner subquery returns no course IDs and the final result is correctly empty.

## Query 16 — Classify Students as Senior or Junior

**Objective:** Use `DATEDIFF()` and a `CASE WHEN` expression to label each student 'Senior' if more than 4 years have passed since their `EnrollmentDate` relative to today's date, otherwise 'Junior'.

**Query**
```sql
SELECT
    StudentID,
    FirstName,
    LastName,
    EnrollmentDate,
    CASE
        WHEN DATEDIFF(CURRENT_DATE, EnrollmentDate) / 365.25 > 4 THEN 'Senior'
        ELSE 'Junior'
    END AS StudentStatus
FROM Students;
```

**Output**

| StudentID | FirstName | LastName | EnrollmentDate | StudentStatus |
| --- | --- | --- | --- | --- |
| 1 | John | Doe | 2022-08-01 | Senior |
| 2 | Jane | Smith | 2021-08-01 | Senior |

> Evaluated against today's date (2026-09-22): John enrolled 2022-08-01 (~4.14 years ago) and Jane enrolled 2021-08-01 (~5.14 years ago) — both exceed 4 years, so both are correctly labeled **Senior**.


## 5. How the Outputs Were Generated

The outputs in this document are not hand-typed guesses — they were produced by
actually running the script:

1. The schema and sample `INSERT` statements from `Final_Project.sql` were loaded
   into an in-memory **SQLite** database (Python's built-in `sqlite3` module) via a
   verification script, `run_queries.py`.
2. Each `SELECT` query from the script was executed in order, exactly as written,
   with the following MySQL-only functions mapped to SQLite equivalents so they
   would run (results are numerically/logically identical to MySQL):
   - `YEAR(date)` → a registered Python function returning the first 4 characters
     of the date string as an integer.
   - `DATEDIFF(a, b)` → a registered Python function returning `(a - b).days`.
   - `CONCAT(a, ' ', b)` → SQLite's `||` string-concatenation operator.
   - `CURRENT_DATE` was pinned to **2026-09-22** so Query 16's output is
     reproducible on any machine reading this document.
3. Each result set's column names and rows were captured and rendered as a
   Markdown table.

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.executescript(schema_sql)      # from Final_Project.sql, Section 1
cur.executescript(insert_sql)      # from Final_Project.sql, Section 2

conn.create_function("YEAR", 1, lambda d: int(str(d)[:4]))
conn.create_function("DATEDIFF", 2, lambda a, b: (parse(a) - parse(b)).days)

cur.execute(select_query)          # each query from Final_Project.sql, Section 3
columns = [d[0] for d in cur.description]
rows = cur.fetchall()
```

The full harness is included alongside this README as `run_queries.py`, so the
outputs can be regenerated and re-verified at any time by running:

```bash
python3 run_queries.py
```
